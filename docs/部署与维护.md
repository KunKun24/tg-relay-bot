# 部署与维护

适用版本 2.0.0，Python 3.12。当前安装目录 `/path/to/双向机器人克隆`，服务账号 www。主平台与克隆由同一个 systemd 服务管理，不需要 Web、Redis 或额外数据库服务。

## 目录与运行方式

业务模块在 [relayapp](../relayapp/)，[兼容入口](../relay_bot.py) 仅调用模块化 Runtime。服务定义见 [tg-relay.service](../deploy/tg-relay.service)。Token 和运行数据库仅留在服务器，源码包不包含它们。

当前关键位置：

| 项目 | 位置 |
| --- | --- |
| 服务 | tg-relay.service |
| 环境配置 | `.env`，参考 [.env.example](../.env.example) |
| 数据库 | `relay_bot.db`，可用 RELAY_DB_PATH 配置 |
| 虚拟环境 | `.venv` |
| 运行日志 | `/path/to/logs/tg-relay-v2.log` |
| 一致备份 | `backups/` |
| 私聊实发回执 | `data/live-smoke.json` |
| 切换前私人备份 | `/path/to/.relay-upgrade-xxxx/cutover/` |

`.env`、数据库及 WAL/SHM 由 www 持有，权限 600；data/logs/backups 目录 700；代码目录 755、源码及普通配置 644。编辑工具可能原子替换文件并改变所有者，修改私有配置后要检查权限。

## 当前服务操作

在项目目录执行：

```bash
systemctl status tg-relay.service
systemctl show tg-relay.service -p MainPID -p ActiveState -p SubState -p NRestarts
runuser -u www -- .venv/bin/python scripts/health.py
systemctl restart tg-relay.service
systemctl stop tg-relay.service
```

日志为 systemd 的 append 文件，读取需要 root 权限；www 无需直接读取该日志。健康检查用只读 SQLite，心跳需小于 90 秒并且数据库 quick_check=ok。healthy 表示监督进程与数据库状态正常，不代表所有克隆凭据都有效；同时查看 clones_actual、clones_desired 和后台失败原因。

服务已开机启用，异常退出 5 秒后重启，优雅停止等待上限 180 秒。退出保留克隆期望状态；原本 DISCONNECTED 的克隆不会因重启自行恢复。重启只尝试启动通知主管理员 123456789，不向全部客户广播；运行中的持久广播按原状态继续。

不要手动再启动第二个主进程，也不要在其他服务器用同一 Token 同时轮询。进程锁只能阻止本机使用同一项目数据目录的重复实例，不能消除其他服务器上的轮询冲突。

## 新环境安装

1. 安装 Python 3.12、venv、pip 和系统根证书，创建服务账号及项目目录。
2. 解压源码并创建独立虚拟环境。当前机器依赖版本固定在 [requirements.txt](../requirements.txt)。
3. 按 [.env.example](../.env.example) 建立私有 `.env`，填写真实主 Token、管理员 ID 和数据库路径。主用户名以 Telegram 实际 getMe 返回为准。
4. 需要迁移业务时，先恢复一致数据库快照；空库由 Runtime 首次启动自动建表，不要把测试库当业务库。
5. 校正代码/私有文件权限，调整服务定义中的绝对路径、User/Group 和日志目录。
6. 校验服务定义，安装后启动并检查心跳和克隆状态。

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
systemd-analyze verify deploy/tg-relay.service
# 将核对后的服务定义安装到 /etc/systemd/system/tg-relay.service
systemctl daemon-reload
systemctl enable --now tg-relay.service
```

BotFather 中确认主机器人允许所需官方 Bot Management 能力；一键创建使用 Telegram 官方流程，不保存用户账号 Session 或验证码。目标群/频道需按界面要求授予机器人和操作者权限。自定义表情是否可用仍取决于 Bot API 资格与投递场景。

## DNS 修正

当前机器的系统解析异常，因此私有环境配置了 TELEGRAM_API_IPS，仅对本进程访问 api.telegram.org 生效。HTTPS URL 主机名仍为 api.telegram.org，证书校验保持开启，未修改系统 hosts 或全机 DNS。

当前经证书校验的配置为：

```dotenv
TELEGRAM_API_IPS=149.154.166.110,149.154.167.220,149.154.167.99
```

这些地址不是永久保证。若连接超时，先检查本机解析与官方域名证书，重新核验地址；系统 DNS 修好后可清空此值并重启。新环境默认留空。不要使用 verify=False 或未经验证的第三方 API 代理。

## 数据备份与迁移复核

在线一致备份使用 SQLite backup API，包含已提交的 WAL 数据，不能只复制活跃主数据库文件。

```bash
runuser -u www -- .venv/bin/python scripts/backup.py
```

输出备份绝对路径、大小和 integrity。备份文件名为 UTC 时间，权限 600；没有自动删除历史备份，也没有新增定时任务。跨机器保存时同时私下保存 `.env`、服务定义和版本号；这些敏感内容不得放入公开源码包。

[迁移核对脚本](../scripts/verify_migration.py) 仅在尚不存在的隔离副本执行迁移，对所有原表原列原行比较并验证重复迁移幂等，拒绝覆盖已有目标：

```bash
.venv/bin/python scripts/verify_migration.py \
  --source /绝对路径/升级前.sqlite3 \
  --target /绝对路径/尚不存在的隔离副本.sqlite3 \
  --report /绝对路径/尚不存在的核对报告.json
```

旧版本完整备份及隔离验证报告留在服务器私人备份目录。报告和数据库有业务隐私，不进入源码交付。

## 恢复及版本回滚

恢复前停止服务，确认 MainPID=0，保存当前数据库的一致快照和私有环境。先在隔离路径验证待恢复备份的 PRAGMA integrity_check，并核对其业务时间点。使用 SQLite backup API 将其恢复到**新文件**，校正 www 所有权和 600 权限，再把 RELAY_DB_PATH 指向这个新文件；不要覆盖正在使用的数据库，也不要混用不同备份的 db、wal、shm。重启后运行健康检查、检查全部克隆期望状态和实际状态。

仅回滚 v2 程序时应配套兼容 schema。回到原 v1 则必须一起恢复切换前原代码、原服务定义、原数据库快照与对应环境，并先做离线验证。直接将旧代码指向 v2 数据库存在会话结构等不兼容。切换前快照不包含升级后的新消息、订单和配置；恢复该快照会回退这部分业务，需要先明确接受该恢复时间点。

重放任何发送中记录前应检查 UNKNOWN 状态，不能因恢复数据库就假设 Telegram 没收到消息。

## 广播与故障处理

- InvalidToken：由对应所有者提供同一个 Telegram 机器人的有效新 Token，通过主平台“更换 Token”操作；不能拿另一个机器人替代。
- TimedOut、NetworkError、RetryAfter 启动失败：服务按 30 秒至 15 分钟退避自动恢复，最多同时 2 个。断开、删除及无效 Token 不在自动恢复范围。
- Forbidden、Chat not found：先检查目标是否启动/屏蔽机器人、群权限及聊天 ID，软件不能强制投递给不可达用户。
- 广播 UNKNOWN：管理员明确重试或跳过，重试可能重复，跳过可能漏发。成功收件人不自动重发。
- 支付：只有支付查询返回已支付状态才结算；响应提供的标识/金额/币种逐项核对。付款链路配置发生变化时应使用受控测试订单验证，不能仅凭离线测试推断商户已可用。
- 占用或 Conflict：先排查其他主机或手动进程，不要不断重启多个实例。

## 回归与真实验收脚本

完整隔离回归：

```bash
runuser -u www -- env PYTHONDONTWRITEBYTECODE=1 PYTHON_DOTENV_DISABLED=1 \
  MAIN_BOT_TOKEN=OFFLINE_TEST MAIN_ADMIN_ID=123456789 \
  RELAY_DB_PATH=/tmp/relay-tests-unused.sqlite3 \
  .venv/bin/python -m pytest -p no:cacheprovider -q
```

[管理员实发脚本](../scripts/live_smoke.py) 读取当前配置，在临时 SQLite 中只向主管理员私聊发送，显式确认后才运行。它不会启动 polling、不会修改生产数据库或向客户群发，但会产生 Telegram 真实消息。测试克隆必须由主管理员本人拥有，并且对应管理员能够接收其私聊。

```bash
runuser -u www -- .venv/bin/python scripts/live_smoke.py \
  --clone-id 22 --confirm-admin-private-send
```

本次真实实发覆盖主菜单、主后台、会员表情/颜色按钮、单接收者持久广播、克隆后台及欢迎语。未实测真实充值、客户群/频道权限、所有克隆全路径、规模压测和长期稳定性，详见 [升级验收报告](升级验收报告.md)。
